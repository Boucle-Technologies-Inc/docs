Every merchant's program runs in one of two settings modes, set from **Dashboard → Settings → Program rules**. This page covers what that means for a client reading `rewardExpiryDays`, `pointsEnabled`, and related fields from the [read endpoints](/api/read-endpoints) — and the one governed setting that currently has no field in the API at all.

<Warning>
  **The public API is in private beta and not generally available during Ruffus's initial pilot.** The read endpoints this page describes return `404 not_found` for merchants who haven't been explicitly enabled for early access. See [API Overview](/api/overview) for details, or email [hello@ruffus.app](mailto:hello@ruffus.app).
</Warning>

## Simple mode vs. custom mode

By default, a merchant's program runs in **simple mode**: on Ruffus's recommended settings for stamp cooldown, PIN requirements, reward expiry, the nearby-reminder geofence, referral bonus amount, and points-earn tuning. Nothing is stored per-merchant for those fields in any meaningful sense — the merchant's own columns are ignored, and the recommended constant wins.

A merchant can switch to **custom mode** from the dashboard to take ownership of that same set of fields. The switch is reversible: reverting to simple mode does not reset the merchant's stored values, so switching back to custom later restores exactly what they had tuned.

<Note>
  `pointsEnabled`, `referralsEnabled`, `pointsPerStamp`, and `tiersEnabled` are **not** part of this governed set — whether a feature is on is the merchant's own choice in either mode, never overridden by the recommended defaults. Only *how* an enabled feature behaves (cooldown length, expiry window, referral bonus size, per-dollar rate) is governed.
</Note>

### What this means for `GET /v1/cards` and `GET /v1/cards/{id}`

Both endpoints return the **effective** value of every governed field, not the raw stored column. Concretely, `rewardExpiryDays` in the response body already reflects `resolveRules(settingsMode, …)` server-side:

- Merchant in simple mode, any stored `rewardExpiryDays`: the API returns Ruffus's current recommended value (`null` — no expiry — as of this writing).
- Merchant in custom mode: the API returns exactly what the merchant configured.

There is no `settingsMode` or `simple`/`custom` field in the card payload itself, and no way to tell from the response alone which mode produced a given value — a `null` `rewardExpiryDays` on a simple-mode merchant and a `null` on a custom-mode merchant who explicitly chose "never expires" are indistinguishable over the API. If your integration needs to react to a mode *change* rather than the resulting value, there is currently no field or webhook event for that; poll the field and diff it yourself.

`pointsEnabled` is not governed, so it is always the merchant's raw stored value regardless of settings mode — no resolution step applies to it.

There are no write endpoints for any of these fields. Settings changes are dashboard-only; the API is read-only for program configuration.

## Two expiry clocks, one exposed

Ruffus runs two independent expiry mechanisms. They answer different questions and clear different things:

| | Reward expiry | Inactivity expiry |
|---|---|---|
| Question it answers | Does an *earned* reward have a deadline? | Does a *dormant* balance eventually clear? |
| What it clears | One unredeemed reward | Stamps, points, and unclaimed rewards together |
| Default | Off (`rewardExpiryDays: null`) | Off |
| Resets on | N/A — a reward either gets redeemed or expires | Any visit — stamping, redeeming, or earning points resets the clock to zero |
| Governed field | `loyaltyPrograms.rewardExpiryDays` | `loyaltyPrograms.progressExpiryMonths` |
| In the public API | **Yes** — `rewardExpiryDays` on the card object | **No** — not selected by any `/v1` route as of this writing |

### Reward expiry

Documented in full at [Stamps and Rewards](/loyalty-card/stamps-and-rewards#reward-expiry-optional). The field you read from the API, `rewardExpiryDays`, is a nullable integer — `null` means no expiry, otherwise the number of days after a reward unlocks before it voids.

### Inactivity expiry

A separate, merchant-configured window (in months) after which a customer's *entire* balance on a card — stamps, points, and any unredeemed reward — clears if they have not visited at all in that window. Turning it on for the first time does not retroactively evaluate anyone's existing last-visit date: every current member is given a full, fresh window measured from the day the setting is turned on, so nobody is cleared for time that already elapsed before the merchant opted in.

Customers receive a warning email two weeks ahead of their clear date, and the date itself is surfaced on their card view and on their Apple/Google Wallet pass — none of which currently has an API-visible counterpart. There is no `progressExpiryMonths` field on the card object, no `membership.expiresAt` on the [membership balance](/api/read-endpoints#membership-balances) response, and no webhook event fires when a balance clears via this path (compare the [event catalog](/api/webhooks#event-catalog), which covers enrollment, stamps, and reward unlock/redemption only). Reading a customer's stamp and points balance directly via [`GET /v1/customers/{ref}/memberships`](/api/read-endpoints#membership-balances) after the fact is the only way to observe the result today.

<Warning>
  If your integration depends on knowing a program's inactivity-expiry window or a specific customer's clear date, there is no supported way to read either through the `/v1` API today. Treat this as a dashboard-only feature until a field or event ships for it.
</Warning>
