All endpoints below are `POST`, live under `https://api.ruffus.app/v1`, and follow the [conventions](/api/overview) for auth, pagination, and errors. Every endpoint here supports the `Idempotency-Key` header described in [Idempotency](/api/overview#idempotency) — use it whenever a request might be retried by your infrastructure.

## Enroll a customer

`POST /v1/customers` · scope `customers:write`

Attaches an **already-registered** Ruffus customer to a location's cards — the API can't create a brand-new customer from scratch (email/phone alone isn't enough consent under Law 25). New people should join via a QR code or your CSV import.

```bash
curl -X POST https://api.ruffus.app/v1/customers \
  -H "X-Api-Key: rk_live_..." \
  -H "Content-Type: application/json" \
  -d '{ "email": "ana@example.com", "location_id": "9b2f..." }'
```

Body — exactly one of `email` or `phone`, plus `location_id`:

| Field | Type | Notes |
| --- | --- | --- |
| `email` | string | |
| `phone` | string | E.164, or 10-digit NANP |
| `location_id` | string (UUID) | |

Enrolls the customer into every active card at that location — the same set they'd get from scanning the location's QR code.

```json
{
  "object": "customer_enrollment",
  "customerId": "7e31…",
  "locationId": "9b2f…",
  "membershipIds": ["m9f4…"],
  "created": true
}
```

Re-enrolling someone already on those cards is a no-op: `200` with `created: false`, same body otherwise. `email`/`phone` that don't match a registered customer return `404 not_found`.

Enrolling someone this way emails them: customers who already have a Ruffus account are told you added them to your program, and the email includes a link to remove the card if they didn't ask for it (usable only while the card has no stamps, rewards, or points). Enroll customers who asked to join — at your checkout, at the register — not harvested lists.

## Issue a stamp

`POST /v1/customers/{ref}/earn` · scope `loyalty:write`

The customer must already be enrolled at the location — this endpoint doesn't auto-enroll. Enroll first with the endpoint above if you're not sure.

```bash
curl -X POST https://api.ruffus.app/v1/customers/7e31.../earn \
  -H "X-Api-Key: rk_live_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order_48213-stamp" \
  -d '{ "location_id": "9b2f...", "stamps": 1, "amount_cents": 1234, "external_id": "order_48213" }'
```

| Field | Type | Notes |
| --- | --- | --- |
| `location_id` | string (UUID) | required |
| `card_id` | string (UUID) | optional — if omitted, resolves to the oldest shared card, which may not be the one you intended; multi-card merchants should always pass it explicitly. Must be the card's `family` id (see `GET /v1/cards`), not a per-location clone's own `id` — passing a clone id returns `404 not_found` |
| `stamps` | integer | 1–100, default 1 |
| `amount_cents` | integer | optional — the sale total in cents (e.g. `1234` = $12.34). **Required** when the target card's points earn mode is **per amount spent** — omitting it there returns `409 conflict` rather than granting the stamp with zero points. Ignored for a **flat**-points or no-points card. No upper bound: this is a machine-supplied total from your own system, not a staff-entered counter amount, so it isn't subject to the manual entry's typo guard — a genuine $15,000 sale earns its full points. |
| `external_id` | string | optional, 1–255 chars — your own dedup key (see below) |

```json
{
  "object": "earn_result",
  "customerId": "7e31…",
  "locationId": "9b2f…",
  "cardId": "c1a2…",
  "membershipId": "m9f4…",
  "stamps": 1,
  "points": 30,
  "balance": 7,
  "unlockedRewardIds": [],
  "deduplicated": false
}
```

This endpoint earns exactly what an in-person visit earns: active [campaign](/dashboard/campaigns) bonus stamps and [VIP tier](/loyalty-card/tiers) perks apply on top of the base `stamps` you request, the same as a staff scan or a tap-to-earn visit — so the `stamps` in the response is the *total actually granted*, which can exceed what you requested when a bonus applies. A referral payout owed to whoever referred this customer is also triggered on their first-ever stamp, same as any other visit. `points` reflects [Points](/loyalty-card/points), when enabled on the target card — computed from `amount_cents` on a **per amount spent** card, or from the granted stamp count on a **flat**-points card; `0` when points aren't enabled. `unlockedRewardIds` is populated when this grant crosses the card's threshold.

**Deduplication by `external_id`:** pass a stable key that identifies the real-world event (e.g. your own order or POS transaction id). A second request reusing the same `external_id` on the same membership doesn't re-grant — it returns `200` with `deduplicated: true` and the current balance, unchanged. `stamps` and `points` are `0` on that response: they report what *this* call granted, which is nothing — not a replay of what the original call granted. This is independent of `Idempotency-Key`: use `external_id` to make the *business action* idempotent even from a different request, and `Idempotency-Key` to make an individual *HTTP retry* safe.

A customer not enrolled at `location_id` returns `409 conflict` — enroll them first.

## Adjust a balance

`POST /v1/customers/{ref}/adjust` · scope `loyalty:write`

For corrections — refunds, staff mistakes, manual reconciliation — without rewriting history. Adjustments are recorded as their own compensating event, never edits to a past stamp grant.

```bash
curl -X POST https://api.ruffus.app/v1/customers/7e31.../adjust \
  -H "X-Api-Key: rk_live_..." \
  -H "Content-Type: application/json" \
  -d '{ "location_id": "9b2f...", "stamps": -1, "external_id": "refund_9911" }'
```

| Field | Type | Notes |
| --- | --- | --- |
| `location_id` | string (UUID) | required |
| `card_id` | string (UUID) | optional, same resolution behavior and `family`-id requirement as `/earn` (see above) |
| `stamps` | integer | non-zero, magnitude ≤ 100 — positive to add, negative to remove |
| `external_id` | string | optional, same dedup semantics as `/earn` |

A positive `stamps` behaves exactly like `/earn` (can unlock a reward). A negative `stamps` removes **at most the customer's current balance** — it floors at zero rather than going negative, and never claws back a reward that's already been minted. Because of the floor, the amount actually removed can be less than what you requested:

```json
{
  "object": "adjust_result",
  "customerId": "7e31…",
  "locationId": "9b2f…",
  "cardId": "c1a2…",
  "membershipId": "m9f4…",
  "requested": -3,
  "applied": -2,
  "balance": 0,
  "unlockedRewardIds": [],
  "deduplicated": false
}
```

Same enrollment requirement, `external_id` dedup, and error shape as `/earn`.

## Redeem a reward

`POST /v1/customers/{ref}/redeem` · scope `loyalty:write`

```bash
curl -X POST https://api.ruffus.app/v1/customers/7e31.../redeem \
  -H "X-Api-Key: rk_live_..." \
  -H "Content-Type: application/json" \
  -d '{ "short_code": "482913", "location_id": "9b2f..." }'
```

Body — exactly one of `reward_id` or `short_code`, plus `location_id`:

| Field | Type | Notes |
| --- | --- | --- |
| `reward_id` | string (UUID) | |
| `short_code` | string | the 6-digit code the customer shows you; must currently be `available` |
| `location_id` | string (UUID) | required |

```json
{
  "object": "redeem_result",
  "rewardId": "r5c8…",
  "customerId": "7e31…",
  "locationId": "9b2f…",
  "cardId": "c1a2…",
  "membershipId": "m9f4…"
}
```

Unlike `/earn` and `/adjust`, whose `cardId` is always the card's `family` id, `/redeem`'s `cardId` is the specific program row that granted the reward — for a granular multi-location merchant this can be a per-location clone id, not the family id.

The reward is looked up scoped to your merchant and this customer — one belonging to someone else, or to a different merchant, returns `404 not_found` either way. A reward tied to a different location than the one you passed returns `409 conflict`. A reward that's already been redeemed or has expired returns `409 conflict`. If the location's Ruffus subscription isn't active, `402 subscription_inactive`.

## Typical use

These four endpoints are the same primitives your POS, e-commerce checkout, or back-office tooling can call directly to drive loyalty — mirroring what staff-scan and the [Shopify integration](/integrations/shopify) do internally.
