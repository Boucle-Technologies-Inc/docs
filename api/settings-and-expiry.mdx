Every merchant's program runs in one of two settings modes, set from **Dashboard → Settings → Program rules**. This page covers what that means for a client reading `pointsEnabled` and related fields from the [read endpoints](/api/read-endpoints) — and why the governed settings, including inactivity expiry, currently have no field in the API at all.

<Warning>
  **The public API is in private beta and not generally available during Ruffus's initial pilot.** The read endpoints this page describes return `404 not_found` for merchants who haven't been explicitly enabled for early access. See [API Overview](/api/overview) for details, or email [hello@ruffus.app](mailto:hello@ruffus.app).
</Warning>

## Simple mode vs. custom mode

By default, a merchant's program runs in **simple mode**: on Ruffus's recommended settings for stamp cooldown, PIN requirements, inactivity-expiry window, the nearby-reminder geofence, referral bonus amount, and points-earn tuning. Nothing is stored per-merchant for those fields in any meaningful sense — the merchant's own columns are ignored, and the recommended constant wins.

A merchant can switch to **custom mode** from the dashboard to take ownership of that same set of fields. The switch is reversible: reverting to simple mode does not reset the merchant's stored values, so switching back to custom later restores exactly what they had tuned.

<Note>
  `pointsEnabled`, `referralsEnabled`, `pointsPerStamp`, and `tiersEnabled` are **not** part of this governed set — whether a feature is on is the merchant's own choice in either mode, never overridden by the recommended defaults. Only _how_ an enabled feature behaves (cooldown length, expiry window, referral bonus size, per-dollar rate) is governed.
</Note>

### What this means for `GET /v1/cards` and `GET /v1/cards/{id}`

None of the governed fields above — stamp cooldown, PIN requirements, inactivity-expiry window, the nearby-reminder geofence, referral bonus amount, or points-earn tuning — currently have a field on the card object, so simple vs. custom mode makes no observable difference in an API response today. `threshold` and `active` are plain merchant-owned values with no simple/custom resolution step. If your integration needs to know a program's cooldown window, its inactivity-expiry setting, or any other governed value, there is currently no field or webhook event for that — these remain dashboard-only.

`pointsEnabled` is not governed, so it is always the merchant's raw stored value regardless of settings mode — no resolution step applies to it.

There are no write endpoints for any of these fields. Settings changes are dashboard-only; the API is read-only for program configuration.

## Inactivity expiry

Ruffus has a single expiry mechanism: inactivity expiry. It doesn't put a deadline on any one reward — it clears a customer's entire dormant balance (stamps, points, and any unredeemed reward together) after a long stretch with no visit at all. See [Stamps and Rewards](/loyalty-card/stamps-and-rewards#inactivity-expiry-optional) for the customer-facing behavior.

|  | Inactivity expiry |
| --- | --- |
| What it clears | Stamps, points, and an unredeemed reward together |
| Default | Off |
| Resets on | Any visit — stamping, redeeming, or earning points resets the clock to zero |
| Governed field | `loyaltyPrograms.progressExpiryMonths` |
| In the public API | **No** — not selected by any `/v1` route as of this writing |

A merchant-configured window (in months) after which a customer's _entire_ balance on a card — stamps, points, and any unredeemed reward — clears if they have not visited at all in that window. Turning it on for the first time does not retroactively evaluate anyone's existing last-visit date: every current member is given a full, fresh window measured from the day the setting is turned on, so nobody is cleared for time that already elapsed before the merchant opted in.

Customers receive a warning email two weeks ahead of their clear date, and the date itself is surfaced on their card view and on their Apple/Google Wallet pass — none of which currently has an API-visible counterpart. There is no `progressExpiryMonths` field on the card object, no `membership.expiresAt` on the [membership balance](/api/read-endpoints#membership-balances) response, and no webhook event fires when a balance clears via this path (compare the [event catalog](/api/webhooks#event-catalog), which covers enrollment, stamps, and reward unlock/redemption only). Reading a customer's stamp and points balance directly via [`GET /v1/customers/{ref}/memberships`](/api/read-endpoints#membership-balances) after the fact is the only way to observe the result today.

<Warning>
  If your integration depends on knowing a program's inactivity-expiry window or a specific customer's clear date, there is no supported way to read either through the `/v1` API today. Treat this as a dashboard-only feature until a field or event ships for it.
</Warning>
